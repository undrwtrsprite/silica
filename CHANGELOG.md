### Investigation: first-person hand lighting and Vulkan stutter

- **Hand (fixed, both backends):** `Tessellator.addVertex` duplicated vertices 0 and 2 when converting quads to triangles but did not copy the normal, so duplicated vertices had a zero normal (ambient-only lighting): gradients and a diagonal wedge on lit models (visible on the first-person arm). Fixed by copying the normal. `Tessellator.setNormal` also sign-extended negative bytes, clobbering the other components; now masked with `& 255`. (The original `x * 128.0F` quirk, which flips +X normals, is left as is.)
- **Stutter:** MoltenVK acquires the Metal drawable lazily inside `vkQueueSubmit`; in windowed mode the 3-drawable pool recycles at display cadence, so submit blocks for about one refresh interval (12 ms on a 60 Hz display, which also hard-caps it at 60 FPS). Measured with `-Dbetavk.vkstats=true` (per-frame fence/acquire/submit/present times). Swapchain acquire and present cost about 0.01 ms. In fullscreen 1920x1080 (monitor 0): Vulkan 398 FPS avg, p99 9.8 ms; GL 197 FPS avg, p99 8.7 ms.
- `VkCore`: submit and present now run on a dedicated thread (`Vulkan submit`), with the game thread waiting only to reuse a slot; this did not remove the stall (back-pressure moved to the fence wait) but is kept since it never blocks the game thread on encoding.
- `platform.Display`: `-Dbetavk.monitor=N` opens the window on a given monitor; `getDesktopDisplayMode()` initialises GLFW on demand (starting with `--fullscreen` crashed with an NPE before).
- Benchmarks must pin the monitor: `BENCH_MONITOR=0 scripts/bench.sh ...`.

### Vulkan correctness pass

- **Fog (fixed):** the GL backend advertises `GL_NV_fog_distance`, so the game uses radial (eye-distance) fog on GL; the Vulkan backend used planar depth and reported no support. Vulkan now emulates `GL_EYE_RADIAL_NV` in the vertex shader (`alpha.w` flag) and reports `supportsFogDistanceNV() == true`. Measured with the new `scripts/imgdiff.py` against the GL frame at the same path position: mean colour per horizontal band now matches within 0.1/255 (was up to 8/255 low at the horizon); overall mean |diff| 7.79 -> 3.94.
- **Residual difference (open, minor):** fine texel-level noise on terrain (mostly red channel) plus random snow particles and mobs; cause of the terrain grain not established.
- **Resize / fullscreen on Vulkan:** verified with `-Dbetavk.windowtest=true` (1100x650 -> 1920x1080 -> 1100x650); swapchain recreated each time, GUI re-laid-out.
- **Pipeline cache** is persisted to `~/Library/Caches/beta-vulkan/pipeline.cache` (`-Dbetavk.cachedir` overrides); saved at exit, loaded at start.
- `Backends.create()` logs backend capabilities. GL reports occlusionQueries/VBO/fogDistanceNV all true; Vulkan reports occlusionQueries=false (not implemented) and vbo=false.
- New: `scripts/imgdiff.py` (screenshot diff by band, amplified diff map).

### Phase 3 step 8 (part): occlusion culling on Vulkan

- `VulkanRenderer`: `GL_ARB_occlusion_query` implemented on `VkQueryPool` (one pool of 4096 per frame slot). Results are collected when a slot is reused (fence signalled), so `RESULT_AVAILABLE` turns true about 2 frames after issue; pools are reset lazily in the frame's upload command buffer on first use. Queries that cannot be issued (pool full, minimised window) report "visible". `supportsOcclusionQueries()` is now true. `VkCore.onSlotAcquired` hook added.
- Finding: the game only issues occlusion queries when `gameSettings.advancedOpengl` ("Advanced OpenGL") is on, which is off by default; no earlier benchmark used occlusion culling on either backend.
- Verified: with Advanced OpenGL on at far distance, rendered chunks drop 398 -> 113 (289 occluded) on Vulkan and 341 -> 112 (270 occluded) on GL; GL and Vulkan frames match with nothing wrongly culled.
- Benchmark switch `BENCH_ADVANCED=1` (`-Dbetavk.bench.advanced`); result JSON now includes the game's renderer counters (`renderers_debug`).
- Benchmark (monitor 0, avg FPS / 1% low, culling ON): far GL 256 / 120 vs Vulkan 491 / 150; normal GL 323 / 139 vs Vulkan 567 / 178; short GL 603 / 247 vs Vulkan 589 / 171. Effect of culling: GL +26% / +44% / +33% avg FPS; Vulkan -1% / +3% / 0%. Vulkan is bound by main-thread CPU work (about 1.7-2 ms per frame), not by the GPU, so reducing GPU work does not help it; at short distance GL with culling (603) matches Vulkan (589).

### Phase 3 step 8: chunk meshing on worker threads (`-Dbetavk.meshworkers=N`, default 0)

New: `dev.betavk.mesh.{MeshPool, MeshWorker, MeshResult, MeshTest}`. Far chunk rebuilds (the 2/frame the game already defers) are meshed on workers from a `ChunkCache` snapshot taken on the game thread; workers record vertices (capturing `Tessellator`) and the game thread applies them to display lists within a 2 ms/frame budget. Near chunks (within 16 blocks, i.e. block edits) stay synchronous.
Isolation, by construction: per-worker `Tessellator`, shallow `Block` copies (`Block.shadowCopy`; RenderBlocks rewrites bounds), `WorldChunkManager` (scratch arrays shared with terrain generation), `isLit` flag; `Vec3D`/`AxisAlignedBB` pools bypassed on workers; tile-entity maps not read on workers; non-overworld dimensions stay synchronous.
`mc-src` changes: `Tessellator` (per-thread `get()`, capture mode, `drawCaptured`; 80 references re-pointed), `Block` (`Cloneable`, `shadowCopy`), `Chunk.markLit`, `ChunkCache` (worker-aware manager and tile entities), `WorldRenderer` (`buildMesh`, `applyMesh`, `updateRendererFar`, generation-tagged job tracking, `isOrphan`/`isBuilt`), `RenderGlobal` (applies results, sends far renderers to workers), `Vec3D`, `AxisAlignedBB`, `RenderBlocks` and `BlockStep` (block identity compared by id: `tallGrass`, `grass`, `stairSingle`).
Verification: differential test (`-Dbetavk.meshtest=true`) meshes sampled sections synchronously and on 3-4 workers (all jobs at once) and compares used vertex slots exactly: 4 seeds, >10,500 sections, ~19M vertices, 0 mismatches; workers 3.3x faster wall than serial. Bugs found by it: workers using the game thread's `Vec3D` pool (crashed the game thread), identity comparisons against `Block` singletons (tall-grass offset, slab check).
Bug found by a user report ("chunks disappear"): a renderer retargeted while its job was in flight had the old job's result dropped as stale and the rebuild request lost, leaving the new target unmeshed. Fixed with per-job generation tracking; verified with fault injection (`-Dbetavk.meshdelay=ms` delays results): 121 stale drops, 0 orphaned renderers. Natural-latency holes in view (new `holes_*` metrics): 1.08 avg with workers vs 1.26 without.

### Chunk generation speed (user report: "chunk gen seems slow")

Measured first (`GenStats`, `-Dbetavk.bench` output `gen_summary`): terrain ~0.9-1.0 ms/chunk, populate (trees/ores/lakes) ~0.85 ms/chunk, lighting ~0.5 ms/chunk, all on the game thread; world start ~0.95-1.1 s for ~290 chunks (terrain 280-300 ms, populate ~230 ms, lighting ~110 ms, rest JIT warm-up).
- **Default meshing workers = 1** (`-Dbetavk.meshworkers`): measured on 4 P + 6 E cores, 1 worker +3-4% avg FPS and up to +10% 1% lows vs game-thread meshing; 2-3 workers no better (contention with the game thread, more GC). Workers run at minimum priority.
- **Rejected experiment:** raising the far-section budget above 2 per frame (`-Dbetavk.meshbudget`, default stays 2) cut FPS ~40% (202 -> 119): the original cap sheds work for sections that are retargeted before being built. Sections in view converge within 1 s even in the original path (`holes_startup_per_second`).
- **Terrain prefetch** (`dev.betavk.gen.GenPool`, `-Dbetavk.genworkers=N`, default 2): worker threads with private `ChunkProviderGenerate` instances (private `WorldChunkManager`, scratch buffers) generate terrain ahead of demand, nearest first, around the player (radius up to 18 chunks by render distance) and around the spawn at world creation. `Chunk.func_1024_c` was split into `heightAndSky` (worker) and `neighbourLighting` (game thread, reads neighbours and schedules lighting). `ChunkProviderGenerate.provideChunk` takes a prefetched chunk, waits for a running job, or cancels a queued one and generates inline.
  Differential test (`-Dbetavk.gentest=true`): 4 seeds, ~3,700 chunks, blocks/metadata/sky light/heightmap identical to the game-thread provider (3 concurrent workers; 0.72 ms/chunk serial, 3x faster wall).
  Effect: terrain generated on the game thread during a 40 s run 726-804 chunks -> 363-562; world start 1067-1135 ms -> 904-1078 ms. Populate and lighting still run on the game thread and are now the largest generation costs.
- New: `World.isChunkLoaded`, `Minecraft.runTick` calls `GenPool.onTick`, `Minecraft.changeWorld2` calls `GenPool.prefetchSpawn`.

### Phase 4 step 13 and Phase 6: JVM flags, soak

- JVM (normal distance, 2 runs, GL): default G1 202-220 FPS / 4 ms max pause; fixed pre-touched 2 GB G1 198-211 FPS (+1.3 GB RSS); ParallelGC 200-201 (15 ms pauses); generational ZGC 197-200. Default G1 with a heap cap is used (`GCProfile.balanced`).
- 10-minute Vulkan soak with shipped defaults (160k frames): average FPS per quarter 265.5 / 268.1 / 265.6 / 267.1 (no degradation), 0 orphaned chunks, 0 mesh fallbacks, 5 stale mesh results dropped of 165k, max GC pause 16 ms. Live heap after GC rises 152 -> 816 MB (66 MB/min) in this worst-case straight-line flight; the original code path (all my threading off) rises at 72 MB/min, so it is pre-existing. Cause (class histogram): the world's scheduled block-tick queue (water/lava ticks scheduled as chunks generate) backs up at ~1,000 processed ticks per game tick (740k pending entries after 150 s) plus chunk byte arrays.
- `NextTickListEntry.hashCode` packed x/z/y/id into overlapping bit fields, so the dedupe `HashSet` treeified almost every bucket (`HashMap$TreeNode`); replaced by a proper mix (the set is only used for de-duplication; ordering comes from the `TreeSet`). Treeification is gone; ~120 B per pending tick instead of ~141 B; heap growth on the original path in the same flight fell from 72 to 55.7 MB/min (-23%) at unchanged FPS.
- Note: MoltenVK logs `VK_ERROR_FEATURE_NOT_PRESENT: Metal does not support disabling primitive restart` once at startup (strip/fan topologies); harmless.

### Deferred populate (opt-in, `-Dbetavk.deferpopulate=1`, default off)

`ChunkProvider.prepareChunk` can queue populate (FIFO, drained by `GenPool.onTick` at 3 ms/tick, 6 ms when >12 pending; chunks loaded inside a populate are populated at once; spawn area drained before the first frame; `Benchmark` drains before saving). Populate cannot run on workers: it writes live into neighbouring chunks in an order-dependent way.
- World vs immediate populate (same seed/spawn, 625 chunks): 4,258 of 18.9M blocks differ (0.023%), 271 in solid shape (0.0014%); two immediate runs differ by 201 (lava). Not byte-identical because all neighbours are loaded before each populate runs. `RAW TERRAIN` check fails on one edge chunk for the same reason.
- Vulkan, windowed, far/normal, 2 rounds: avg FPS 269-273 both ways, p99 11.1-11.3 ms both ways, max frame 57-69 ms off vs 67-80 ms on. No benefit measured, so it stays off by default. Results in `bench/results/defer-{off,on}-r{1,2}`.

### Fix: missing chunks at far render distance (Vulkan mesh memory)

Symptom (user report): holes in the terrain where caves show through. Cause: all chunk meshes were sub-allocated from one 256 MB vertex buffer; at far render distance it was 254/256 MB full and `glDrawArrays` silently dropped every draw that did not fit ("display-list arena full; dropping a draw", 1,000-9,900 times per 60 s far run in every earlier benchmark log; I had filtered those logs and my `holes` metric only counts sections with no mesh at all). Fix: mesh memory now grows on demand in 256 MB buffers (up to 8); far distance settles at 2 x 256 MB. Far/normal after the fix: 267.6 / 264.7 FPS, 0 dropped draws. `scripts/bench.sh` now warns when a run logs a dropped draw or an exception. The Benchmark `-Dbetavk.bench.settle=true` census (12 s hold after the flight, counts unloaded chunks and unmeshed renderers) was added while looking for this; it cannot see dropped draws.

### Validation layers (Khronos, via Homebrew vulkan-validationlayers + loader)
`-Dbetavk.validate=true` (see `bench/validation/` for the loader/ICD/manifest files and the env: `VK_LAYER_PATH`, `VK_ICD_FILENAMES`, `-Dorg.lwjgl.vulkan.libname=<brew loader>`). A far-distance flight and the resize/fullscreen test run with 0 errors/warnings after one real fix: an empty frame signalled a fence its slot had not waited on or reset. Remaining by design: acquire (game thread) and present (submit thread) touch the swapchain concurrently; the layer flags this occasionally. Serialising them under a lock was tried; it is only safe with a short-timeout acquire and is used only under `-Dbetavk.validate`, because I could not show it free of cost (a measured 270 -> 147 FPS drop turned out to be the launcher's 120 Hz hero animation competing for WindowServer; fixed by pausing the animation while the game runs or the window is inactive).

### Walking hitch fix: chunk saving moved off the game thread (user report: hitches when walking around)

### LOD: distant terrain (Options > Video > LOD: Off / 24 / 32 / 48 / 64 / 96 chunks, default 48; saved as `lod`)
Beyond the chunks meshed in full detail the world is drawn as cheap low-poly tiles out to the LOD distance, which pushes the view from about 200 blocks (the renderer grid is capped there) to up to 1,536 blocks.
- `dev.betavk.lod.LodManager`: tiles of 64x64 blocks = 8x8 cells of 8 blocks (height and colour of the surface at each cell's centre). A low-priority worker (`-Dbetavk.lodworkers`, default 1) samples the real terrain generator with its own provider (`ChunkProviderGenerate.lodTerrain`: the same noise and biome surface, no caves, no trees, no lighting), so the distant terrain matches the detailed one on approach. Grass uses the biome colour map, snow/ice in cold biomes by the game's own temperature rule, water at sea level.
- Each tile is one display list (top quad per cell plus skirts to lower neighbours; vertex colours with a baked directional shade and the current daylight, so it darkens at night; drawn untextured, no culling, under the normal fog, 2.5 blocks below the sampled height so it hides under the detailed terrain where they overlap). Lists are recorded 4 per frame, re-recorded a few at a time when the daylight changes, and dropped when far behind the player.
- `EntityRenderer`: far plane and fog extend to the LOD distance; the LOD pass runs right after the terrain pass. LOD is off in the Nether.
Measured (fullscreen, Vulkan, flight benchmark): short distance + LOD 64 397 FPS (short alone about 399) with the view out to 1,024 blocks instead of 64; normal distance 369.4 -> 361.2 FPS with LOD 64 (about 2%), p99 9.9 -> 9.7 ms, RSS +54 MB; far distance + LOD 64 339.5 FPS (340 without). About 1,030 tiles (16 chunks each, 10 ms per tile on the worker) fill the ring within about 10 s. Slow frames with LOD on are the same MoltenVK waits and periodic block-update ticks as without it.
Known limits of v1: no trees or caves in the distance, flat colours, one 8-block resolution at every distance, the sampling repeats work the detailed chunk generation also does near the boundary, and tiles are regenerated each session (not cached to disk).
`-Dbetavk.bench.lod=N` sets the LOD distance in the benchmark, `-Dbetavk.bench.time=N` the world time.

### LOD v2: three detail levels, smooth terrain, disk cache
- **Levels**: level 0 = 4-block cells (64-block tiles) from the edge of the detailed terrain to 384 blocks; level 1 = 8-block cells (128-block tiles) to 768; level 2 = 16-block cells (256-block tiles) to the LOD distance (up to 96 chunks). Every tile is a 16x16 grid; the rings overlap and the coarser level is drawn lower (2.5 / 5 / 9 blocks below the sampled height) so the finer one wins in the overlap.
- **Look**: each cell averages several samples of the real terrain generator (1, 4 or 16 columns per cell); the mesh is a smooth height field with corners shared between cells (and across tile borders), shaded from its slope against the sun for relief, with a little per-cell grain. Forest, rainforest, taiga, seasonal forest and swamp get a dark foliage speckle over the grass to suggest tree cover (population is not run for LOD). Skirts are only drawn on tile borders whose same-level neighbour is not ready yet.
- **Cache**: sampled tiles are written to `<game dir>/lodcache/v2/<seed>/L<level>/<tx>_<tz>.bin` (about 1.7 MB for a 96-chunk LOD) and read back on later sessions: a second run loaded 370 tiles from disk and sampled none. `-Dbetavk.lodcache=0` turns it off, `-Dbetavk.lodworkers=N` sets the sampling threads (default 1-2 by core count).
- **Cost** (fullscreen, Vulkan, flight benchmark, normal distance): LOD 96 372.8 FPS, p99 9.6 ms (369 / 9.9 without LOD); about 590 tiles sampled in the first ~60 s of a fresh world (56 ms per tile on average: level 2 tiles cover 256 chunks).
- Screenshots (`-Dbetavk.lodshot=true -Dbetavk.lodshot.wait=N -Dbetavk.bench.alt=35`: the camera stops, looks at the horizon in four directions once the LOD queue is empty, saves `/tmp/lod-1..4.png`). The pale translucent slabs on the horizon in those shots are the game's clouds, which now show much further out.
- Held-item name: moved down again (41 px above the bottom, 52 with armor or air bubbles); the inventory hover tooltip is back at its original height.

### LOD v3: the real blocks (user request: "use the original blocks as the base so you can barely tell")
The smooth shaded height field was replaced by what the real chunk mesher would draw for a surface:
- **Textured with the game's own atlas**: the top block's real texture on top (grass and leaves in the biome colour from the game's colour maps, snow cover and ice by the game's temperature rule, sand, gravel, stone, water at sea level), real side textures down the cliffs (top block's side, then up to three blocks of dirt, then stone: at most three quads per side), the game's face shading (top 1.0, z faces 0.8, x faces 0.6), and daylight through the lighting state's ambient term at draw time (dusk and night cost nothing and need no re-recording).
- **Five levels**: 1-, 2-, 4-, 8- and 16-block columns, with rings from the edge of the detailed terrain to 192 / 320 / 560 / 960 blocks / the LOD distance (up to 1,536). Tile edges 64 / 128 / 256 / 512 / 512 blocks (a 64x64 grid of cells for the first four levels). Each cell takes the surface height, top block and tint from up to 4x4 column samples of the real terrain generator (`ChunkProviderGenerate.lodTerrain`, low-priority workers, no caves or lighting).
- **Trees**: the population step is not run for LOD, so canopies are approximated at the density of each biome (forest 9 per chunk, rainforest 11, taiga 8, seasonal forest 5, swamp 4, a few in plains), deterministic per chunk, standing on grass: leaf-textured columns with the biome foliage colour and a log-textured trunk column below the crown.
- **Cost control**: meshes are built on the workers into captured vertex data (about 1 ms per tile); the game thread only records them into display lists under a per-frame budget (300k ints, `-Dbetavk.lodbudget`). Each tile is recorded as four quadrant lists so frustum and ring culling work on smaller pieces (a whole big tile drawn for a corner inside its ring was the first version's main cost). A tile is meshed only once its same-level neighbours are sampled (it used to be meshed 2.8 times). Rows of water or ice are one flat quad using the middle texels of the water texture. Faces wind counter-clockwise outward so back-face culling is on.
- **Disk cache** (`lodcache/v4/<seed>/L<level>/`, about 1.8 MB for a 96-chunk LOD, 2-4 KB per tile).
- **Measured** (fullscreen, Vulkan, flight benchmark at normal render distance, steady state after the fill, same session): no LOD 335.6 FPS (p99.9 13.05 ms); LOD 48 299.0 (12.40 ms, RSS +355 MB); LOD 96 291.4 (11.79 ms, RSS +565 MB); 4-7 frames over 14 ms in 40 s in every case. The first versions of this block LOD cost 26-40% (700 draws, 1.1M vertices a frame) before the culling, sub-list and meshing changes above; a fresh 96-chunk fill takes about 1-2 minutes in the background at 2 worker threads.
- Screenshot tool: `-Dbetavk.lodshot=true -Dbetavk.lodshot.wait=N -Dbetavk.bench.alt=12` (`/tmp/lod-1..4.png`, waits for the LOD queue to empty). `-Dbetavk.lodnodraw=true` generates and records everything but draws nothing.
- Known limits: no caves or ores, canopies are approximated (positions differ from the real trees, which appear when you get close), no biome variants of leaves beyond the foliage colour map, water is opaque and flat from a distance.

## LOD v4: real trees

Each tree stands exactly where the game will plant it, with its real trunk (log texture, spruce/birch variants), floating canopy (leaf box with underside, per-block-layer sides, spruce leaf texture, biome/pine/birch tint) and size. Coarse levels (8/16-block cells) draw canopies as leafy blocks and tint sparse ones into the ground colour.
- Checked against the real world: over a 14x14-chunk area every simulated tree matched a real one (176/176 leaf columns, identical heights); the real world had 2 chunks with extra or moved trees (a dungeon or cave room in the chunk shifts its draws; caves are not simulated). ## LOD v4.1: leaves, ice and water
- Canopy per column is now the topmost run of leaves (bridging a single empty layer, which spruce rings need) instead of lowest-to-highest leaf, so big trees no longer get leaf curtains hanging down to the ground.
- 8- and 16-block cells no longer draw leaf boxes unless the cell is at least 70% canopy (8-block only); sparse and far canopies tint the ground instead of standing as dark slabs.
- Water and ice colour is computed, not tiled: the game's translucent water/ice composited over the real sea floor (depth, bed block, light lost per layer), constants calibrated from pixels of the real renderer (deep water about 41,54,165; ice over water about 97,125,177 in daylight). Previously LOD water was brighter and LOD ice almost white.
- Tile cache bumped to v6.

## LOD sampling yields to real chunks
- LOD tile sampling now rests after each tile (three times as long as it worked while real chunks are queued for generation or meshing, half as long otherwise) and waits briefly before starting a tile while the chunk queue is busy. ## Chunk fill-in no longer depends on frame rate
- Cause of "chunks generate super slow": the game handed at most 2 far chunk sections per frame to the meshing worker (the original game's limit), so the world filled in at 2 x FPS sections a second. My benchmarks ran uncapped at 300-400 FPS and never showed it; with Max FPS at 160 it is 320 sections/s, at 60 FPS 120/s, while a Far view is thousands of sections. `MeshPool.farBudget()` is now a rate (`-Dbetavk.meshrate`, default 900 sections/s, 0 = the old fixed 2 per frame), never below 2 per frame.
- Measured, Max FPS 160, flying 40 blocks/s, Far, LOD off, fresh world: sections missing within 96 blocks averaged 95.7 (max 209) before, 0.25 (max 2) after; initial fill about 5 s before, about 1 s after; FPS unchanged (156 vs 158).
- Benchmark knobs added: `betavk.bench.speed` (blocks/s), `betavk.bench.maxfps`. Chunk disk-load timing is now in the gen summary (0.1 ms per chunk, not a factor).

## LOD v4.2: sparse canopies, ice
- Canopies at 2/4/8-block cells are drawn when at least a quarter of the cell is leaves, as a box as wide as that coverage (a sparse spruce is a thin tree, not a bare trunk and not a slab); 16-block cells tint the ground harder (up to 90%) so snowy forests are no longer white. Cache v7.
- Ice colour re-measured with a like-for-like shot (same camera, real chunks vs LOD) at a frozen lake: the earlier calibration used a glancing, shadowed ice pixel. Ice is now the texture's (125,174,255) at 0.62 over the water layers below it over the sea floor, with the ice itself passing full daylight, which reproduces the pale blue (about 160,192,240) the game shows over a shallow lake. ## LOD v4.3: translucent ice
- LOD ice is drawn the way the game draws it: the lake floor as seen through the layers below the ice (water over sea floor), then the real ice texture on top using its own alpha, with blending on for the LOD pass (one block per cell at the two finest levels so the texture mottling shows). Cache v8. Walking benchmark with LOD 48: 299.6 FPS, p99.9 9.9 ms, no holes (no cost from the blend state).

## LOD v4.4: translucent water, reversed-Z depth, ice colour at distance
- Water at the two finest levels is drawn like the game's: the sea floor (its real block texture, lit by the three light levels lost per water layer, black below five layers) with the water texture over it using its own alpha, plus wall skirts where floors step or meet the shore so nothing shows through gaps. Deep water is one black floor and merged runs of a single translucent quad. Cache v9.
- Depth: the Vulkan depth buffer is now reversed (1 at the near plane, 0 at the far plane, compare ops flipped, depth bias negated, clear value 0), with the perspective z built on the CPU as A + B*w (no cancellation). The standard mapping left float depth with about 0.8 blocks of resolution at 800 blocks, which is the z-fighting between LOD levels when zooming at distance; now it is even over the whole range. The projection matrix the game reads (frustum culling) is unchanged.
- Water and ice cells at coarse levels take the colour of their water samples only (snow and shore samples washed them out), and the LOD detail rings moved out (224/384/640/1024 blocks instead of 192/320/560/960).
- Walking benchmark LOD 48 after all of it: 235-251 FPS (was about 296 before translucent water and the blended pass); detail rings left at 192/320/560/960. This is the last change to the hand-rolled LOD; the next step is a Voxy-style design.

## Memory: patched build resident size
- The patched game sat at about 1.3 GB resident at Normal/Short distance against about 0.8 GB in-tree. Not a leak: live heap after GC is 150-200 MB in both. ## Best heap size
- Heavy flight (50 blocks/s, Far, 70 s, two runs per size, patched; G1 with the free ratios): 512 MB fails to start (OutOfMemory); 768 MB runs but spends the most time in GC (about 1.6 s of 70 s, 1% low 59-70 FPS); 1024 and 1536 MB about 1.6-1.8 s GC; 2048 MB and above about 1.0-1.2 s GC; FPS the same from 1024 MB up (248-264 average). Longest pauses grow slightly with size (6-7 ms at 1 GB and 1.5 GB, 10-14 ms at 2 GB and above). In-tree build, same flight at 2 GB: the same behaviour.
- Live heap after GC climbs about 200 MB per 30 s in that flight (243, 433, 650 MB) in both builds: b1.7.3 single player never unloads chunks (nothing adds to the drop set), so memory is roughly 250 MB plus 70 KB per loaded chunk for the whole session. Walking an hour at Far is about 1.5 GB; the fast flight is ten times quicker than walking.
- Normal flight, four runs each: 2 GB and 3 GB caps both stay at 800-870 MB resident (8 of 8). So the free-ratio flags keep memory low and the cap is only the ceiling: default is now 3072 MB (`run-patched.sh`, launcher), 2-4 GB is fine.

## Chunk unloader (patched build only)
- `hooks/world/Unloader`: b1.7.3 single player never unloads a chunk (nothing puts one in the provider's drop set), so memory grew by about 70 KB per chunk seen, and the queue of scheduled block updates (water and lava spreading) grew without bound while flying because chunk generation schedules far more than the 1000 per tick the game handles (1.28 million `NextTickListEntry` after 2.5 minutes at 50 blocks/s). Every tick up to 5 loaded chunks outside the view plus 10 chunks (27 at Far) are put in the game's own drop set, which saves them (asynchronously) and frees them; scheduled updates outside that range are removed (4000 checked per tick, the game would drop them unticked anyway). `-Dbetavk.unload=false` turns it off, `-Dbetavk.unload.margin` and `-Dbetavk.unload.pertick` tune it. Not in the in-tree build.
- Check (`betavk.test=unload`): a gold block placed at spawn, the player flies 1600 blocks away, chunk (0,0) is unloaded after 0.3 s, back at spawn the block is read back from disk and is still there; world and inventory checks still pass.
- 270 s flight at 50 blocks/s: live heap after GC stays at 227-276 MB (without it 238 to 497 MB and climbing, 865 MB at 100 s in an earlier run). Cost: 0.14 ms per tick on average, 1.6 ms at most. FPS equal at walking-flight speed (258 and 245 against 245 and 247); in the extreme flight (about 70 chunks a second) p99 is about 3 ms higher (20.2 against 17.3 ms, two runs each) and 1% low about 7 FPS lower.
- The unloader is now off by default (vanilla keeps every visited chunk loaded and simulated); `-Dbetavk.unload=true` turns it on. Kept for later.
